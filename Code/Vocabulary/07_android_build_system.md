# Section 7 — Android Build System (Q133–Q166)

---

## Gradle Basics (Q133–Q140)

### Q133. What is Gradle?
**Definition:** An open-source build automation tool used to build, test, and package Android apps.
**Core Idea:** Describes HOW to build your project using a Groovy or Kotlin DSL script. Handles dependencies, compilation, packaging.
**How it Works:** Runs tasks in a DAG (directed acyclic graph) — compiles Kotlin → generates R.java → merges resources → packages APK/AAB.
**Example:** `./gradlew assembleDebug` builds the debug APK.
**Interview Insight:** Gradle is incremental — it only rebuilds what changed. Clean builds are slow; incremental builds are fast. Use Gradle build cache and configuration cache to speed up CI.

---

### Q134. What is the Android Gradle Plugin?
**Definition:** The Gradle plugin (`com.android.application` or `com.android.library`) that adds Android-specific build tasks.
**Core Idea:** Adds tasks for compiling resources, generating `R.java`, converting to DEX, signing, and creating APKs.
**How it Works:** Applied in `build.gradle`: `apply plugin: 'com.android.application'`. Provides `android { }` DSL block.
**Example:** `android { compileSdk 34; defaultConfig { applicationId "..." } }` — configured via AGP DSL.
**Interview Insight:** AGP version and Gradle version must be compatible. AGP adds build variants, build types, product flavors — all Android-specific concepts on top of base Gradle.

---

### Q135. What is a Gradle build script?
**Definition:** A `.gradle` (Groovy DSL) or `.gradle.kts` (Kotlin DSL) file that configures a Gradle project or module.
**Core Idea:** Declares plugins, dependencies, configurations, and build logic for a module.
**How it Works:** Groovy DSL: `build.gradle`. Kotlin DSL: `build.gradle.kts`. Kotlin DSL is type-safe and IDE-friendly.
**Example:** `build.gradle.kts` for a module declares `plugins`, `android { }`, and `dependencies { }` blocks.
**Interview Insight:** Kotlin DSL (`.kts`) is now the recommended standard. It gives you autocomplete, refactoring support, and type safety that Groovy DSL lacks.

---

### Q136. What is `build.gradle`?
**Definition:** The module-level build script that defines how a specific module is compiled, tested, and packaged.
**Core Idea:** Two levels: project-level (`./build.gradle`) for global config, and module-level (`./app/build.gradle`) for the app itself.
**How it Works:** Module-level contains: `plugins`, `android { compileSdk, minSdk, targetSdk, buildTypes, productFlavors }`, `dependencies`.
**Example:** `implementation("androidx.lifecycle:lifecycle-viewmodel-ktx:2.7.0")` — adds a dependency.
**Interview Insight:** Project-level `build.gradle` configures all subprojects. Module-level is where you spend most time. In multi-module projects, each module has its own `build.gradle`.

---

### Q137. What is `settings.gradle`?
**Definition:** Declares which modules/subprojects are part of the build and configures the repository resolution.
**Core Idea:** The entry point for Gradle. Tells Gradle which modules exist.
**How it Works:** `include(":app", ":core", ":feature:home")` — declares modules. Also configures plugin/dependency repositories.
**Example:** `include(":app")` in a single-module app. In multi-module: `include(":app", ":core:network", ":core:data")`.
**Interview Insight:** In new Android projects (AGP 7+), `settings.gradle.kts` also defines repository locations (replacing project-level `build.gradle` `allprojects { repositories {} }`).

---

### Q138. What is `gradle.properties`?
**Definition:** A key-value properties file that configures Gradle's JVM settings and project-wide flags.
**Core Idea:** Global build settings — JVM heap size, enabling Android-specific optimizations.
**How it Works:** `org.gradle.jvmargs=-Xmx4g` sets Gradle daemon memory. `android.useAndroidX=true` enables AndroidX.
**Example:** Common settings: `org.gradle.parallel=true`, `org.gradle.caching=true`, `kotlin.code.style=official`.
**Interview Insight:** `gradle.properties` is a performance tuning file. `org.gradle.jvmargs=-Xmx4g -XX:+HeapDumpOnOutOfMemoryError` — gives Gradle daemon more heap to avoid OOM on large projects.

---

### Q139. What is `local.properties`?
**Definition:** A machine-specific properties file that contains local paths (like Android SDK path). NOT committed to version control.
**Core Idea:** Machine-specific config that differs per developer/CI environment.
**How it Works:** Auto-generated by Android Studio: `sdk.dir=/Users/user/Library/Android/sdk`. Can also store local API keys (dev only — not for production secrets).
**Example:** `sdk.dir=/home/dev/Android/Sdk` — tells Gradle where the SDK is installed.
**Interview Insight:** Always add `local.properties` to `.gitignore`. Never put production secrets here — use CI/CD environment variables or a secret management system.

---

### Q140. What is a Gradle task?
**Definition:** A unit of work that Gradle performs — compiling, testing, packaging, signing, etc.
**Core Idea:** Everything Gradle does is a task. Tasks have dependencies on other tasks (DAG).
**How it Works:** `./gradlew tasks` lists all tasks. `assembleDebug` depends on `compileDebugKotlin`, `processDebugResources`, etc.
**Example:** `./gradlew test` runs unit tests. `./gradlew connectedAndroidTest` runs instrumented tests.
**Interview Insight:** Custom Gradle tasks automate repetitive work (versioning, code generation, deploy). Understanding task DAG helps debug slow builds — use `--profile` to see which tasks take longest.

---

## SDK Configuration (Q141–Q144)

### Q141. What is `compileSdkVersion`?
**Definition:** The API level your code is compiled against. Determines which APIs are available at compile time.
**Core Idea:** Compilation tool — doesn't affect the APK or what devices can run it.
**How it Works:** Set to latest stable API to get access to new APIs and better lint warnings. Doesn't change runtime behavior.
**Example:** `compileSdk 34` — you can use Android 14 APIs in your code. IDE shows deprecations and new APIs.
**Interview Insight:** Always set `compileSdk` to the latest stable. It's free — it doesn't affect minimum device support. It just means your build tools know about the latest APIs.

---

### Q142. What is `minSdkVersion`?
**Definition:** The minimum Android API level your app supports. Devices below this level cannot install your app.
**Core Idea:** Determines your user base. Lower `minSdk` = more devices supported, but more compatibility code needed.
**How it Works:** Devices running below `minSdk` are filtered out on Google Play. Lint warns about using APIs above `minSdk` without version checks.
**Example:** `minSdk 26` — only Android 8.0+ devices can install. `minSdk 21` — Android 5.0+ (covers ~99% of active devices).
**Interview Insight:** Use `@RequiresApi(Build.VERSION_CODES.X)` or `if (Build.VERSION.SDK_INT >= Build.VERSION_CODES.X)` guards when using APIs above `minSdk`.

---

### Q143. What is `targetSdkVersion`?
**Definition:** The API level your app is designed and tested for. Tells the system "this app is optimized for this Android version."
**Core Idea:** Controls which new behavior changes the system applies to your app. High `targetSdk` = opt-in to new behaviors.
**How it Works:** A higher `targetSdk` enables new Android security/privacy features (scoped storage, runtime permissions). Google Play requires targeting a recent API level.
**Example:** `targetSdk 34` — your app handles Android 14 permission changes. Background process restrictions apply.
**Interview Insight:** `targetSdk` is a PROMISE to the system: "I handle all behavior changes up to this API level." Not updating `targetSdk` lets apps avoid new restrictions but Google Play enforces minimum `targetSdk`.

---

### Q144. Difference between compile SDK and target SDK?

| | `compileSdk` | `targetSdk` |
|---|---|---|
| Purpose | What APIs you can use in code | What behaviors the system applies |
| Affects APK? | No | Yes (changes runtime behavior) |
| Set to | Latest stable | Latest stable (for Google Play) |
| Danger of not updating | Miss new APIs/lint | Avoid new restrictions (temporary) |

**Interview Insight:** `compileSdk = targetSdk` is the best practice. Both should be the latest stable API. They're technically separate concerns but almost always the same value.

## Build Variants (Q145–Q149)

### Q145. What are build types?
**Definition:** Configurations defining how the app is built — primarily `debug` and `release`, but you can add custom ones.
**Core Idea:** Same code, different build configurations (signing, minification, debugging, flags).
**How it Works:** Defined in `buildTypes { debug { ... } release { ... } }`.

| | Debug | Release |
|---|---|---|
| Signing | Debug keystore | Release keystore |
| Minification | Off | On (R8) |
| Debuggable | Yes | No |
| Assertions | On | Off |

**Interview Insight:** Never ship a debug build. Release builds have minification/obfuscation enabled via R8. Define a `staging` build type for internal testing with release-like settings.

---

### Q146. What is debug build type?
**Definition:** The build configuration for development. Debuggable, not minified, signed with a debug keystore.
**Core Idea:** Safe for development — you can attach a debugger, get detailed stack traces, use `Log`.
**How it Works:** Auto-generated by AGP. Can customize: `debug { applicationIdSuffix ".debug"; versionNameSuffix "-debug" }`.
**Example:** `./gradlew assembleDebug` — builds a debuggable APK with a debug signing key.
**Interview Insight:** Debug builds include extra metadata and are not minified — they're larger and slower than release builds. Never benchmark debug builds.

---

### Q147. What is release build type?
**Definition:** The build configuration for distribution — minified, obfuscated, signed with a release keystore.
**Core Idea:** The build that goes to users. Stripped, fast, and secure.
**How it Works:** `release { minifyEnabled true; proguardFiles ... }`. Must be signed with a release keystore for Play Store upload.
**Example:** `./gradlew bundleRelease` — creates a signed AAB for Play Store upload.
**Interview Insight:** Always test with a release build before shipping. Some bugs only appear in release (ProGuard rules, minification issues, disabled assertions).

---

### Q148. What are product flavors?
**Definition:** Configurations for building different versions of the app with different code, resources, or features.
**Core Idea:** Multiple apps from one codebase — free/paid, different backends, different branding.
**How it Works:** Define in `flavorDimensions` and `productFlavors`. Source sets: `src/free/`, `src/paid/` override `src/main/`.
**Example:** `free` flavor has limited features; `paid` flavor unlocks all. Both build from the same codebase.
**Interview Insight:** Each flavor × build type = a build variant. `free` × `debug` = `freeDebug`. `paid` × `release` = `paidRelease`. CI builds all combinations.

---

### Q149. Difference between build types and product flavors?

| | Build Types | Product Flavors |
|---|---|---|
| Purpose | HOW to build | WHAT to build |
| Examples | debug, release | free, paid, staging, prod |
| Code difference | Minimal (signing, flags) | Can have different code/resources |
| Combinations | debug + release (default) | free×debug, free×release, paid×debug, paid×release |

**Interview Insight:** Build types = deployment configuration. Product flavors = feature/target configuration. They combine to create build variants.

---

## Dependencies (Q150–Q153)

### Q150. What are Gradle dependencies?
**Definition:** External libraries your project depends on, declared in `build.gradle` and resolved by Gradle from repositories (Maven Central, Google).
**Core Idea:** Instead of manually managing JAR files, Gradle downloads and manages dependencies automatically.
**How it Works:** Declared as `implementation("group:artifact:version")`. Gradle resolves from configured repositories (Google, Maven Central).
**Example:** `implementation("com.squareup.retrofit2:retrofit:2.9.0")`
**Interview Insight:** Understand transitive dependencies (your library's libraries). Use `./gradlew dependencies` to visualize the dependency tree and resolve version conflicts.

---

### Q151. What is dependency resolution?
**Definition:** The process Gradle uses to find and download the correct versions of all dependencies (including transitive ones).
**Core Idea:** Multiple libraries may depend on the same library with different versions — Gradle resolves this to one version.
**How it Works:** Gradle follows version resolution strategies (latest, strict, forced). Conflicts are resolved by taking the highest requested version by default.
**Example:** Library A depends on OkHttp 4.10; Library B depends on OkHttp 4.12. Gradle resolves to 4.12 (highest).
**Interview Insight:** Use `constraints` or `force()` to pin specific versions. `./gradlew dependencies --configuration debugRuntimeClasspath` shows the full tree with resolved versions.

---

### Q152. What is a transitive dependency?
**Definition:** A dependency of your dependency — automatically included in your build even though you didn't declare it directly.
**Core Idea:** When you add Retrofit, it brings OkHttp, OkIO, etc. — those are transitive.
**How it Works:** Gradle follows the dependency graph of each declared library and includes their dependencies too.
**Example:** You declare `Retrofit`. Gradle automatically adds `OkHttp`, `Okio`, and `retrofit-converter-gson`.
**Interview Insight:** Transitive dependencies can cause version conflicts. Use `exclude group: '...'` to exclude specific transitive deps. `implementation` prevents transitive deps from leaking to consumers; `api` exposes them.

---

### Q153. Difference between `implementation` and `api`?
**Definition:** Both add a dependency. `implementation` keeps it private (module-internal). `api` exposes it to modules that depend on yours.

| | `implementation` | `api` |
|---|---|---|
| Visible to consumers? | No | Yes |
| Build time | Faster (less recompilation) | Slower (consumers recompile on change) |
| Use when | Module-internal libs | Libs you expose in your module's public API |

**Example:** If `:core` uses `api("retrofit")`, any module depending on `:core` can use Retrofit directly. With `implementation`, they can't.
**Interview Insight:** Prefer `implementation` — it improves build speed (fewer modules recompile on dependency changes). Use `api` only when the library type appears in your module's public API.

## ProGuard / R8 (Q154–Q160)

### Q154. What is ProGuard?
**Definition:** A code shrinking, obfuscation, and optimization tool for Java/Android bytecode.
**Core Idea:** Reduces APK size and makes reverse engineering harder by removing unused code and renaming classes/methods.
**How it Works:** Analyzes bytecode, removes unused code (shrinking), renames classes to `a.b.c` (obfuscation), and inlines/simplifies code (optimization).
**Example:** A Release APK with ProGuard might go from 20MB to 8MB by removing unused classes from libraries.
**Interview Insight:** ProGuard is largely replaced by R8 in modern Android. R8 is faster and does ProGuard + D8 (DEX compilation) in one step.

---

### Q155. What is R8?
**Definition:** Google's replacement for ProGuard — a combined code shrinker, obfuscator, and DEX compiler.
**Core Idea:** R8 replaces both ProGuard (shrinking/obfuscation) and D8 (DEX conversion) in one faster step.
**How it Works:** Reads ProGuard configuration files. Enabled by default in AGP 3.4+. `minifyEnabled true` activates R8.
**Example:** `release { minifyEnabled true; shrinkResources true; proguardFiles getDefaultProguardFile('proguard-android-optimize.txt'), 'proguard-rules.pro' }`
**Interview Insight:** R8 is faster than ProGuard and produces smaller DEX. Same ProGuard rules files work with R8. Always test release builds — R8 can remove code that reflection depends on.

---

### Q156. What problem does ProGuard solve?
**Definition:** Reduces APK size (removes dead code), makes reverse engineering harder (obfuscation), and can improve runtime performance (optimization).
**Core Idea:** Without ProGuard/R8, your APK includes all library code — even code you never use. ProGuard strips it.
**How it Works:** Three steps: Shrink (remove unused) → Obfuscate (rename) → Optimize (simplify bytecode).
**Example:** Retrofit + OkHttp alone is ~500KB. With R8, unused Retrofit converters and OkHttp interceptors you didn't use are removed.
**Interview Insight:** ProGuard/R8 can break reflection-based code (Retrofit uses reflection to parse annotations). You need `-keep` rules to preserve classes used via reflection.

---

### Q157. What is code shrinking?
**Definition:** Removing unused classes, methods, and fields from the APK.
**Core Idea:** Starts from entry points (manifest activities, keep rules), traces reachable code, removes everything else.
**How it Works:** R8 analyzes the call graph. Any class/method not reachable from entry points is removed.
**Example:** You import a library with 100 classes but use only 5. Shrinking removes the other 95 from the APK.
**Interview Insight:** `shrinkResources true` also removes unused resources (layouts, drawables). Combined with code shrinking, it significantly reduces APK size.

---

### Q158. What is code obfuscation?
**Definition:** Renaming classes, methods, and fields to short, meaningless names (`a`, `b`, `c`) to make the APK hard to reverse engineer.
**Core Idea:** Makes decompiled code unreadable, protecting your business logic.
**How it Works:** R8 maintains a `mapping.txt` file: original name → obfuscated name. Use this file to deobfuscate crash stack traces.
**Example:** `com.example.UserRepository.fetchUser()` becomes `a.b.a()` in the APK.
**Interview Insight:** ALWAYS save `mapping.txt` for each release APK. Firebase Crashlytics requires it to show readable crash stack traces. Without it, production crashes are impossible to debug.

---

### Q159. What is a ProGuard rule?
**Definition:** A directive in `proguard-rules.pro` that tells R8 what to keep, ignore, or treat specially.
**Core Idea:** Overrides R8's automatic analysis when you know code is accessed via reflection or JNI.
**How it Works:** File: `proguard-rules.pro`. Applied with `proguardFiles` in `build.gradle`. Syntax: `-keep`, `-keepclassmembers`, `-dontwarn`, etc.
**Example:** Third-party libraries often include their own ProGuard rules in their AAR. Gradle merges all rules automatically.
**Interview Insight:** If your app crashes in release but not debug, suspect a missing ProGuard rule. Enable `-printseeds` and `-printusage` to debug what R8 keeps and removes.

---

### Q160. What does `-keep` mean in ProGuard?
**Definition:** `-keep class com.example.MyClass` tells ProGuard/R8 to NOT remove or rename this class.
**Core Idea:** Prevents shrinking and obfuscation of the specified class/members.
**How it Works:**
- `-keep class Foo { *; }` — keep class AND all members
- `-keepclassmembers class Foo { public *; }` — keep class but only preserve specified members
- `-keepnames class Foo` — prevent renaming but allow removal

**Example:** `@SerializedName` annotated fields for Gson/Retrofit must be kept: `-keepclassmembers class ** { @com.google.gson.annotations.SerializedName <fields>; }`
**Interview Insight:** Too many `-keep` rules = fat APK. Too few = crashes. Start with the minimum, add rules for each crash. Use `@Keep` annotation in Kotlin for specific members.

## Android Build Process (Q161–Q166)

### Q161. What is an APK?
**Definition:** Android Package — the binary package format for distributing and installing Android apps.
**Core Idea:** A ZIP file containing: DEX files (compiled code), resources, assets, manifest, and signing certificate.
**How it Works:** Built by Gradle: compile → resource processing → DEX conversion → packaging → signing.
**Example:** `app-release.apk` — the file you install on a device or upload to Play Store (legacy).
**Interview Insight:** APK is device-specific when uploaded to Play Store (Play re-signs and modifies it). For new uploads, use AAB — Play generates optimized APKs per device configuration.

---

### Q162. What is an AAB (Android App Bundle)?
**Definition:** Android App Bundle — a publishing format that includes all compiled code and resources, letting Google Play generate optimized APKs per device.
**Core Idea:** Upload one AAB; Play Store delivers a device-specific APK (right architecture, screen density, language).
**How it Works:** AAB contains split APK information. Play uses Dynamic Delivery to build and serve the right variant.
**Example:** A user with a `arm64-v8a` phone in English only downloads code + resources for their device, not all architectures/languages.
**Interview Insight:** AAB reduces download size by ~20-40% vs a universal APK. Required for new apps on Google Play since August 2021. Debug builds still use APK format.

---

### Q163. Difference between APK and AAB?

| | APK | AAB |
|---|---|---|
| Purpose | Install directly on device | Upload to Play Store |
| Device specificity | Universal (all configs) | Google Play generates device-specific APKs |
| Size | Larger | Smaller (10-30% reduction) |
| Direct install? | Yes | No — needs Play or `bundletool` |

**Interview Insight:** Use AAB for Play Store releases. Use APK for direct installs (sideloading, internal testing without Play). Local device testing: `./gradlew installDebug` uses APK.

---

### Q164. What is DEX?
**Definition:** Dalvik Executable format — the bytecode format that the Android Runtime (ART) executes. The Android equivalent of JVM `.class` files.
**Core Idea:** Android doesn't run JVM bytecode. Java/Kotlin `.class` files are converted to `.dex` format by D8/R8.
**How it Works:** `javac`/`kotlinc` → `.class` files → D8/R8 → `classes.dex` → packaged in APK.
**Example:** Your entire app (code + libraries) is compiled into one or more `.dex` files.
**Interview Insight:** DEX is optimized for memory-constrained devices — more compact than JVM bytecode, better for mobile. Understanding DEX explains why multidex exists and why 64K methods matter.

---

### Q165. What is multidex?
**Definition:** A solution allowing apps to use more than 65,536 (64K) methods across multiple DEX files.
**Core Idea:** A single DEX file can only reference 64K methods. Large apps + many libraries exceed this limit.
**How it Works:** With multidex enabled, the app is split into `classes.dex`, `classes2.dex`, etc. At runtime, all are loaded.
**Example:** Enable: `multiDexEnabled true` in `build.gradle`. For API < 21: add `implementation 'androidx.multidex:multidex:2.0.1'` and extend `MultiDexApplication`.
**Interview Insight:** Apps targeting API 21+ (Lollipop) have multidex built into ART. The extra setup is only needed for older APIs. R8 with shrinking often reduces method count below 64K, eliminating the need for multidex.

---

### Q166. Why does the 64K method limit exist?
**Definition:** A DEX file stores method references in a 16-bit table, allowing at most 2^16 = 65,536 method references.
**Core Idea:** Historical artifact of the Dalvik VM's instruction format. 16 bits = 64K addressing limit.
**How it Works:** Every method in your code AND every library method counts. A method that's never called still occupies a reference slot.
**Example:** Google Play Services alone contributes ~20K methods. Add Retrofit, RxJava, Glide → easily exceed 64K.
**Interview Insight:** R8 + `minifyEnabled true` removes unused methods, usually keeping the count well below 64K. Multidex is the runtime fix; R8 shrinking is the better prevention.
